# R1-CLI-002 application invocation parity

Status: implemented and validated on `main` as of 2026-09-03.

## Delivered contract

`madmamba run -- <application...>` delegates to the requested child command without capturing its standard streams or rewriting its argument vector. The wrapper returns the child exit status and maps a missing executable to status 127.

Evidence:

- implementation: `madmamba/cli.py` (`run_application` and the `run` subcommand);
- behavioral tests: `tests/test_cli.py` verifies arguments containing spaces/flags, exit status propagation, inherited stdio, and missing-command behavior;
- CI: the installed CLI and test suite passed CPython 3.12, 3.13, 3.14, 3.15-dev, free-threaded 3.13/3.14, macOS, and Windows variants before merge.

## R1.2 runtime boundary

The current `run` command starts a child process. A runtime kernel or `sys.monitoring` lease installed only in the MadMamba parent would not instrument the target application and would therefore create a false implementation claim.

R1.2 must first establish an explicit target-interpreter bootstrap contract. A valid design must preserve the R1-CLI-002 invocation semantics while arranging for MadMamba runtime initialization inside the application interpreter. Parent-only monitoring is explicitly out of scope.

The next runtime iteration should therefore define and test that bootstrap boundary before attaching monitoring callbacks. It must keep stdout/stderr, `sys.argv`, exit status, and exception/SystemExit behavior equivalent to an uninstrumented launch.
